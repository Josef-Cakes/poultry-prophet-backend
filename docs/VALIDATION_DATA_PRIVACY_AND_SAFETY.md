# Validation data privacy and safety

## Data classes

The local validation environment may contain three kinds of data:

1. **Synthetic data** — generated by the 100-day simulator and safe for technical testing when labelled correctly.
2. **Sanitized snapshot data** — copied from a real farm database, with identity fields replaced before use.
3. **Unsanitized source data** — never suitable for a stakeholder demo, Git commit, cloud deployment, or shared evidence folder.

Treat a database backup as sensitive even when it contains no names. Farm operations, financial entries, health events, and notes can identify a person or business when combined.

## Required controls

- Keep validation on a local Docker network and use a validation-only database name.
- Keep `.env.validation` untracked with file mode `600`.
- Use disposable passwords and JWT secrets. Never reuse Render or production credentials.
- Confirm `/api/version` reports `environment=validation` before logging in.
- Keep the source batch read-only in the simulator; create a labelled test copy for edits.
- Back up before restoring or sanitizing a snapshot.
- Review free-text notes, uploaded photos, PDF exports, filenames, and screenshots manually for personal information.
- Do not upload a real snapshot or unsanitized screenshot to GitHub, Render, Google Drive, or a public Facebook group.

## Sanitization limits

`validation-sanitize-local-data.sh` replaces farm names and locations, anonymizes non-validation users, and invalidates handler invites. It does not inspect every free-text field or binary attachment. The team must manually review:

- batch names and bloodline labels;
- event details, observation notes, and task instructions;
- receipt descriptions and transaction counterparties;
- uploaded photos and exported reports;
- browser screenshots and terminal output.

If the team cannot confidently remove identifying information, do not use the snapshot. Use a clean synthetic database instead.

## Evidence handling

For capstone validation evidence, prefer screenshots of the local validation UI with synthetic or sanitized records. Keep the artifact directory outside Git and share only the minimum files required by the adviser. If a screenshot includes an email, token, password, database URL, or personal note, redact it before submission.

## Incident response

If a production credential appears in a local file, commit, screenshot, or log:

1. Stop sharing the file and do not push it further.
2. Revoke and rotate the credential immediately.
3. Remove the exposed copy from the working tree and Git history if it was committed.
4. Check Render, database, and repository access logs.
5. Record the incident and the remediation for the project adviser.

Deleting a file from the latest commit is not enough when the secret exists in earlier Git history.
